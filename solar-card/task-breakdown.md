### 0.1 世界演化规则（由 D1 确定，建议直接写进契约）

```
玩家发消息
   ↓
① 注入：当前世界快照（短） + 本回合相关设定/人物（按需检索）
   ↓
② 判定与生成：解析玩家意图 → 生成正文
     └─ 同一回合内，世界侧也推进一格：NPC 会办事、势力会动、事件会发酵
        （即"玩家什么都不做"时，本回合仍然发生世界侧变化）
   ↓
③ 写回：数值/位置/人物/事件状态 → 变量；本回合摘要 → 记忆层
   ↓
等待玩家下一条消息（世界时钟停在这里，不自己走）
```

三条附带规则：

- **时间粒度**：**默认 1 回合 = 5 分钟**（剧情需要时可拉长或压缩，但要在正文里说清）。大刻度用「时段（晨/昼/昏/夜）+ 日」，推进由剧情与玩家行动决定（例如玩家说"睡一觉"才跳到次日），模型不得偷偷跳时间。这条同时是网络战"3 回合内查到人 ≈ 15 分钟"的计时基准。
- **世界侧推进必须有产出**：每回合至少一条可感知的世界侧变化（有人做了什么 / 某个消息传来 / 某个期限逼近），否则"自由跑团"会退化成"玩家一个人的独角戏"。
- **token 纪律**：世界状态要**增量注入**——常驻快照保持很短，长内容（城市志、势力史）走按需检索，绝不每回合全量塞。

### 0.2 判定契约（**强判定** / 由 D7 修订：轻判定 → 强判定）

判定元素要**露给玩家看**：技能、目标值、修正明细、骰面、结果档，全部展示。这是"可玩性"的来源，也是这张卡和普通叙事卡的分水岭。

**唯一不能变的原则：骰子必须由代码掷。** 语言模型没有真随机，"它自己掷"等于编数字；强判定下玩家会盯着骰面看，编一次就穿帮。

#### 判定制式（提案 · COC 式 d100 掷低｜已按"属性满级 20"重算）

```
目标值 = 属性×3 + 技能×5 + 情境修正
  · 属性 1–20 → 3–60      · 技能 0–5 → 0–25      · 合计封顶 85
  · 难度用"修正"表达：简单 +20 / 普通 0 / 困难 −20 / 极难 −40

掷 d100，与目标值比较：
  d100 ≤ 目标值/2        → 大成功
  目标值/2 < d100 ≤ 目标值  → 成功
  目标值 < d100 ≤ 目标值+10 → 勉强成功（成功，但附带代价/后患）
  目标值+10 < d100 ≤ 95    → 失败
  d100 > 95               → 大失败
```

取样的手感（含难度修正后）：

| 角色档位 | 属性 | 技能 | 目标值 | 对"普通难度"把握 | 对"极难（−40）" |
|---|---|---|---|---|---|
| 新手 | 8 | 1 | 29 | 29% | 几乎无望 |
| 受训 | 12 | 2 | 46 | 46% | 6% |
| 专业 | 15 | 3 | 60 | 60% | 20% |
| 顶尖 | 18 | 5 | 79 | 79% | 39% |
| 满级 | 20 | 5 | 85 | 85% | 45% |

选它的理由：**属性满级 20 与技能 0–5 是两个量纲**，只有 100 点粒度的 d100 能同时容纳（`属性×3` 给 60 点上限，`技能×5` 给 25 点，加起来 85 正好留出余量）；难度做成可见修正比藏一个 DC 更直观；"勉强成功"这一档保留了"代价成功"，失败仍然必须推进剧情。

两条防膨胀硬规则：**单次判定只能用 1 项属性 + 1 项技能**（不叠多属性）；**目标值封顶 85（常规）**——属性 20 + 技能 5 = 85，所以常规满级者仍不是必成。

**芯片 / 古代遗物把属性推到 25 时**：目标值可达 **100**，此时"失败"与"大失败"两档自然消失（档位规则不变，只是区间被占满）——这就是"碾压一切"的数学表现。合成种开局智力 20 属于"起点就在别人终点"的特例。

> 备选：也可以改用赛博朋克原味的"d10 + 属性 + 技能 vs 难度值"，但那会让 d10 的随机性盖过技能差异（技能只有 0–5），技能等级变得没手感，所以不推荐。

#### 骰源策略（**已定：方案 A 预掷骰池**）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A 预掷骰池** | 每回合开始时前端预掷 3–5 个 d100 注入提示词，模型"先声明判定 → 再按顺序取数" | 便宜（一次注入）、实现简单 | 模型理论上可能挑数字；靠"按顺序 + 先声明后取数"约束 |
| **B 两段式真掷** | 模型先输出判定申请（技能/难度/修正）→ 前端掷骰 → 回填结果 → 继续生成 | 每次判定都是真随机，零作弊空间，最像真跑团 | 判定回合的生成次数翻倍（token 约 ×2），实现更复杂（要处理中断续写） |

建议：**M2a 先用 A 跑通，B 作为后续升级项**——两套共用同一份判定数据结构，切换时不动其它模块。

#### 展示层（强判定的核心体验）

- 模型只输出**结构化判定块**（固定模板，字段：判定名 / 技能 / 目标值 / 修正明细 / 骰面 / 结果档），不自由发挥写长段。
- 前端与楼层正则把它渲染成**终端风判定面板**（参考 2080 的"⚡ 行动判定"折叠面板，换成终末地黄黑配色）。
- 面板里的骰面来自变量里记录的**代码骰值**，可事后核对；这也是 M2 验收的抽查项。

#### 其余规则

| 项 | 强判定的取值 |
|---|---|
| **触发条件** | 结果不确定 **且** 失败有实质后果。确定能做、无关紧要、已付出足够代价 → 不判定，直接给结果 |
| **每回合次数** | 常规 1–3 次；大战斗放开到"每拍一次"。判定块要短，避免 token 膨胀 |
| **修正来源** | 属性、技能、装备、处境（掩体/位置/光线）、状态（受伤/疲劳/透支）、关系与人脉 |
| **数值可见** | 玩家能看到自己的属性、技能等级、目标值与修正明细 → 需要角色面板与创建向导点数分配 |
| **失败处理** | 失败必须推进剧情（新麻烦/资源损耗/时间流逝），大失败要留下可追踪的后果 |

顺序约定：判定与"世界侧推进一格"（§0.1）在同一回合内都要发生，顺序是**先判定玩家行动，再让世界侧推进**。

## 1. 什么是"宿主依赖"（回答你的问题）

角色卡本质是一份**数据**（JSON 或 PNG），它**不能带扩展、不能自己执行代码**。所以每一份能力必须归到三类之一：

| 类别 | 含义 | 玩家要做什么 | 本卡的例子 |
|---|---|---|---|
| **宿主依赖** `host_required` | 卡带不了，必须玩家在自己酒馆里**安装/开启**的东西 | 手动安装或打开开关 | **酒馆助手（TavernHelper）扩展**、酒馆助手的**「渲染前端」开关**、以及 ST 本体。少任何一个，卡里的界面就是死按钮 |
| **随卡封装** `embedded_required` | 写在卡数据里，导入卡自动带上 | 什么都不用做 | 状态栏正则、开场白、世界书条目、（若走 MVU）schema 脚本 |
| **远程加载** `remote_runtime` | 卡里只有一个 URL，运行时才去下载 | 需要能访问网络/镜像 | 前端 bundle（jsDelivr）、地图底图、字体 |

拿九条会举例：玩家**必须装酒馆助手并开启前端渲染**（宿主依赖），否则开场白里那个金色「展开·九条会」按钮点不动；按钮背后的 Vue 应用是**运行时从 CDN 拉的**（远程加载）；开场白与两条正则则**随卡封装**。

**为什么这个区分重要**：它决定①安装说明怎么写、②出问题先怀疑哪一层、③要不要做镜像兜底与版本锁定。所以后面每份方案我都会标清"需要装 / 随卡带 / 远程拉"。

> 顺带回答可能的下一问：**MVU 也是宿主依赖**。这正是我建议先用 chat 变量的原因——少一个"玩家没装就跑不起来"的环节。

## 5. 风险（v2）

| 风险 | 说明 | 应对 |
|---|---|---|
| "开放性"范围失控 | 越开放越依赖模型自觉，易变成"什么都能做但都不成立" | M2 先规定"可自由做的事"的边界清单，再放开发 |
| 回合制世界演化变成空转 | 每回合世界侧没有实质变化，"自由跑团"退化成独角戏 | §0.1 硬性要求：每回合至少一条可感知的世界侧变化 |
| 世界状态越滚越大 | 长跑几十回合后，注入内容撑爆上下文 | 分层摘要（世界/地点/人物）+ 增量注入；把 token 预算写进 T2.5 验收 |
| 世界自演化与 token 预算冲突 | 世界状态越多，每回合注入越大 | T2.5 预算表 + 分层摘要（世界层/地点层/人物层） |
| 尺度开关三处联动 | 提示词/设定/UI 不同步，会"说好规避却仍然发生" | T2.7 单一定义源；两个量表 × 两档的**四种组合**各跑一遍验收 |
| 支族表与世界书将来冲突 | 现在手写 12 支族，将来世界书接入可能对不上 | T1.9 表结构按世界书字段设计，接入时做映射 |
| NPC 运行时生成的一致性 | 同一 NPC 越写越走样 | T1.8 登记字段 + 每次注入在场 NPC 卡片摘要 |
| **模型伪造骰点** | 模型自己"编"一个数字，或无视骰池自己算结果，判定失去可信度 | 骰池由前端注入并留档；提示词明令禁止自掷；M2 验收抽查"正文结果 vs 骰池留档"是否对得上 |
| 判定过密 | 一路掷骰把自由跑团变成骰子机，节奏碎 | §0.2 规定常规每回合 1–3 次、大战斗才放开 + 明确"不判定"的三种情形 |
| **判定块吃掉 token 预算**（强判定新增的主风险） | 每回合都输出完整判定面板，长期游玩下上下文与费用明显上升 | 判定块用固定短模板；正文与判定块分开计量并写进 T6.3 预算 |
| 强判定变成"掷骰模拟器" | 玩家只盯数值，剧情沦为掷骰的注脚 | 失败与大失败必须推进剧情；"勉强成功"强制附带代价；世界侧每回合仍要推进一格 |
| 骰值可被模型挑选（方案 A） | 先看到骰池再决定判什么，判定失真 | 硬约束"先声明判定、再按顺序取数"；留档可核对；必要时升到方案 B 两段式 |
| 数值膨胀 | 属性/技能/装备修正叠加后目标值溢出 d100 区间 | 目标值封顶 85（属性×3 + 技能×5）；单次判定只用 1 属性 + 1 技能；装备与处境只做修正不做叠乘 | 
| **三系统规则膨胀** | 魔法/网络战/战斗各带资源与修正，提示词和 UI 一起变重，玩家学不动 | 三个子系统共用同一套 7 属性 + 21 技能与同一份骰池；资源各只留 1–2 个；按 战斗→魔法→网络战 分期上线 |
| 子系统之间的判定叠加 | 同一回合黑入+战斗+魔法各判一次，骰池不够用、正文碎 | T1.15 共存规则硬约束：每回合仍只取 0–2 个骰值，其余作叙事铺陈 |

## 6. 还需要你定的（按重要性）

1. **经验点发放节奏**：每场遭遇 / 每章 / 每次里程碑给多少？能否自由分配到任意属性？（上限已定 20，缺"多快到"）
2. **芯片与古代遗物的稀缺度**：25 点档是长期目标还是中后期就能摸到？古遗物要不要绑定具体遗迹地点？

6. **创建向导深度**：三个下拉就开局，还是多步（外貌 + 出身 + 立场 + 属性分配 + 支族特性）全套？
